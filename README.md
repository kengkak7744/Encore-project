# Encore — ระบบติดตามศิลปินและผู้ช่วยแฟนเพลง

เว็บ Next.js, API/worker Express, PostgreSQL + pgvector และ Ollama สำหรับติดตามศิลปิน คอนเสิร์ต ข่าว และงบทริป

โค้ดโครงการอยู่ที่ [Encore-project](https://github.com/kengkak7744/Encore-project)

โฟลเดอร์ที่ใช้งานคือ `D:\senior project` ส่วนโฟลเดอร์เก่าบน `C:` คงไว้ตามเดิม แชตและสรุปข่าวใช้ `qwen3:8b` และค้นเอกสารด้วย `qwen3-embedding:0.6b`; ตัวเพิ่มประวัติอัตโนมัติใช้ `encore-biography:qwen3.8-27b` (Qwen3.8 27B UD-IQ4_XS) โดยเรียก Ollama ของผู้ใช้บนเครื่องนี้โดยตรงผ่านพอร์ต 11434 และใช้ GPU เครื่องนี้ ประวัติตั้งต้น 37 โปรไฟล์ตรวจและเรียบเรียงก่อนนำเข้า ส่วนประวัติที่ AI เพิ่มจะมีป้ายระบุชัดเจน

## เริ่มใช้งานบนเครื่อง

ต้องมี Node.js 24+, Docker Desktop และ Ollama

```powershell
npm ci
ollama pull qwen3:8b
ollama pull qwen3-embedding:0.6b
npm run biography:setup
docker compose up -d --build
```

เปิด <http://localhost:3000> และดูสถานะที่ <http://localhost:3000/status> งาน seed เริ่มพร้อม Compose และเพิ่ม 37 โปรไฟล์ (30 ศิลปิน/วง + สมาชิก 4EVE 7 คน) พร้อมประวัติสั้น ประวัติแบ่งหัวข้อ และลิงก์อ้างอิง เครื่องหมายตรวจยืนยันบนโปรไฟล์หมายถึง **ข้อมูลประวัติ** มีแหล่งรองรับ ไม่ได้หมายความว่าทุกบัญชีโซเชียลผ่านการตรวจแล้ว สำหรับฐานข้อมูลเดิมให้รัน `docker compose run --rm --build seed` เพื่อเพิ่มช่วงประวัติที่ยังไม่มี โดยไม่ทับช่วงที่ผู้ดูแลแก้ไว้ worker ตรวจคอนเสิร์ตและข่าวหนึ่งรอบทันที แล้ววนทุกหนึ่งชั่วโมงเมื่อ container ทำงานอยู่ หน้า `/status` โหลดสถานะใหม่ทุก 1 นาทีเมื่อเปิดแท็บอยู่; สีแดงหมายถึงรอบล่าสุดผิดพลาดหรือข้อมูลเกินเวลา หลังเพิ่มหรือแก้คีย์ใน `.env` ให้สร้าง container ใหม่ด้วย `docker compose up -d --build --force-recreate api worker web`

หากต้องการบัญชีผู้ดูแล ตั้ง `ADMIN_EMAIL` และ `ADMIN_PASSWORD` (อย่างน้อย 12 ตัวอักษร) ในไฟล์ `.env` ที่ root ก่อนสั่ง `docker compose up` หรือ `docker compose run --rm seed` อีกครั้ง; email ที่มีอยู่แล้วจะไม่ถูกยกระดับเป็นผู้ดูแลอัตโนมัติ  ตั้ง `POSTGRES_PASSWORD` และ `DATABASE_URL` ให้ตรงกันก่อนสร้างฐานข้อมูลใหม่ อย่าใช้ค่าเริ่มต้นบนเซิร์ฟเวอร์

สำหรับพัฒนาเว็บ/API แยกกัน ใช้ `docker compose up -d db`, `npm run dev:api`, `npm run dev:worker`, `npm run dev:web` ตามลำดับ  ตัวแปรของ API ดู [apps/server/.env.example](./apps/server/.env.example); เว็บดู [apps/web/.env.example](./apps/web/.env.example)

คีย์ใน `.env` ที่ root ถูกส่งให้ container ผ่าน Compose: `TICKETMASTER_API_KEY` ใช้ดึงงานในไทยตาม `TICKETMASTER_COUNTRY_CODE` และค้นงานต่างประเทศของศิลปินในระบบ; `INSTAGRAM_GRAPH_ACCESS_TOKEN` กับ `INSTAGRAM_GRAPH_IG_USER_ID` ใช้ Business Discovery สำหรับบัญชีศิลปินที่ผู้ดูแลตรวจยืนยันแล้ว; `GOOGLE_ROUTES_ENABLED=true` กับ `GOOGLE_ROUTES_API_KEY` ใช้ระยะทางขับรถในงบทริป ค่าโดยสารยังเป็น **ราคาประมาณ** ตรวจวันหมดอายุของ token ตาม `INSTAGRAM_GRAPH_TOKEN_EXPIRES_AT` และเก็บคีย์ไว้ใน `.env` เท่านั้น  `META_APP_ID`/`META_APP_SECRET` ยังไม่ถูกใช้ในขั้นตอนอ่านโพสต์นี้และไม่ได้ส่งเข้า container

```powershell
npm run typecheck
npm test
npm run build
docker compose logs -f worker
```

## เพิ่มประวัติด้วย local AI อัตโนมัติ

`biography-worker` ตรวจคิวทุก 1 นาที และทำงาน **23:00–00:00 เวลา Asia/Bangkok** ทุกวัน ทำทีละโปรไฟล์ที่ไม่มีแถวใน `artist_biography_sections` แม้มีประวัติสั้นแล้ว; ศิลปินที่มีประวัติแบ่งหัวข้อจะไม่เข้าคิว แต่ละโปรไฟล์ลองไม่เกินหนึ่งครั้งต่อคืน รวมไม่เกิน 10 ครั้งต่อคืน ไม่ทำงานชดเชยนอกเวลา เครื่องและ Docker ต้องเปิดอยู่ในช่วงนี้

1. อ่านแหล่งใน `artist_sources` และเว็บไซต์ที่ยืนยันแล้วก่อน; ค้น Wikipedia ไทย/อังกฤษอัตโนมัติด้วยชื่อที่ตรงกันเมื่อแหล่งไม่พอ ตรวจ robots.txt สำหรับหน้าเว็บ และปฏิเสธปลายทางในเครือข่ายส่วนตัว
2. Qwen3.8 27B เรียบเรียงภาษาไทย 3–4 หัวข้อจากข้อความที่อ่านได้ เลือกรหัสหลักฐานให้ระบบคัดข้อความตรงและ URL รายหัวข้อ ห้ามเติมข้อเท็จจริงจากความจำโมเดล และคงชื่ออังกฤษตามต้นทางเมื่อไม่มีชื่อไทยที่ยืนยัน
3. ตรวจรูปแบบ ตัวตน ข้อความคัดตรง และให้โมเดลตรวจข้ออ้างอีกครั้ง; ถ้าไม่ผ่านให้แก้ตามผลตรวจได้อีกหนึ่งรอบ ก่อนบันทึกทั้งหมดใน transaction เดียว ตรวจซ้ำว่าโปรไฟล์ยังว่างและไม่มีคนแก้ระหว่างทำงาน
4. เมื่อเที่ยงคืนยกเลิกงานที่ยังไม่เสร็จ; เมื่อข้อมูลไม่พอ/AI หลุดเก็บเหตุผลและลองคืนถัดไป หลังใช้โมเดล unload เพื่อคืนหน่วยความจำ GPU

เลือก [Qwen3.8 27B](https://huggingface.co/Qwen/Qwen3.8-27B) ตามคำแก้ล่าสุดให้ใช้รุ่นใหม่ ผู้พัฒนารายงาน IFBench 79.5 และปรับปรุงงานค้นคว้า/การทำตามคำสั่งเหนือรุ่นก่อน; รุ่นที่ติดตั้งคือ [Unsloth UD-IQ4_XS ~14.3 GB](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF/blob/main/Qwen3.8-27B-UD-IQ4_XS.gguf) เพื่อเผื่อ context 8,192 และ buffer บน RTX 5060 Ti 16 GB (RAM เครื่อง 32 GB) คะแนนโมเดลเต็มไม่ใช่คะแนนของ quant นี้ และยังไม่ได้ benchmark เปรียบเทียบทุกโมเดล

Ollama ที่เปิดอยู่บน Windows เก็บโมเดลตาม `OLLAMA_MODELS=D:\AI\models` ทั้งแชตและประวัติใช้ native endpoint `http://localhost:11434` เดียวกัน แต่ระบุ model คนละชื่อ; worker ใน Docker เรียก `http://host.docker.internal:11434` จึงไม่มี Ollama สำหรับประวัติแยกใน Docker `npm run biography:setup` ดาวน์โหลดผ่าน native Ollama แล้วสร้าง alias จาก text weights ที่ตรึง SHA256 โดยไม่รวม vision projector เพื่อประหยัด VRAM โมเดลใหญ่กับแชตอาจต้องสลับโหลดเมื่อ VRAM ไม่พอพร้อมกัน การตรวจด้วย AI ไม่รับประกันความถูกต้องทั้งหมด หน้าโปรไฟล์ระบุว่าเรียบเรียงด้วย AI และยังไม่ตรวจทานโดยผู้ดูแล ดูคิว/heartbeat ที่ `/status` และร่าง/ต้นทาง/ข้อผิดพลาดที่ `/admin/biographies` (ผู้ดูแลเท่านั้น)

ผลตรวจ 3 ต.ค. 2569: ฐานจริงยังมี 37 โปรไฟล์/117 หัวข้อและคิวว่าง; Qwen3.8 ข้อความล้วนค้น Tilly Birds เองใน DB แยก ตรวจ/แก้ร่าง/เผยแพร่ 3 หัวข้อใน **131.09 วินาที** แล้วคืนถัดไปข้ามเมื่อมีประวัติแล้ว วัด `ollama ps` ได้ **100% GPU, context 8192, memory ~13 GB**; `nvidia-smi` ใช้รวม 14,810/16,311 MiB และเหลือ 1,243 MiB แล้ว unload หลังจบ worker ใน Docker เรียก `http://host.docker.internal:11434` ได้ HTTP 200 และพบ model ที่ตั้งไว้ ตัวตรวจรักษาชื่อเพลงที่มีเครื่องหมายคำถามและปฏิเสธคำอ้างความนิยม/การเติบโตที่ไม่มีหลักฐาน ยังไม่ใช่ benchmark ครอบคลุมทุกศิลปินหรือการเดินตารางจริงหลายคืน

ตั้งค่าใน `.env` root: `BIOGRAPHY_ENABLED`, `BIOGRAPHY_MODEL`, `BIOGRAPHY_WINDOW_START`, `BIOGRAPHY_WINDOW_END`, `BIOGRAPHY_MAX_PER_NIGHT`, `BIOGRAPHY_TIMEOUT_SECONDS` แล้วรัน `docker compose up -d --build --force-recreate biography-worker` สำหรับ dev ใช้ `npm run dev:biography` และ `BIOGRAPHY_OLLAMA_URL=http://localhost:11434` ทดลองร่างแบบไม่แก้ฐานข้อมูลด้วย `npm run biography:preview -- tilly-birds` ผู้ดูแลเพิ่มแหล่งเสริมผ่าน `PUT /api/admin/artists/:id/sources` JSON `{ "url": "https://...", "label": "..." }`; การค้นแหล่งอัตโนมัติทำงานได้โดยไม่ต้องใส่ลิงก์นี้

ทดสอบ integration โดยตั้ง `BIOGRAPHY_TEST_DATABASE_URL` เป็นฐานข้อมูลทดสอบที่ชื่อขึ้นต้น `encore_biography_test` แล้วรัน `npm test` (มีการล้าง fixtures เฉพาะ DB นี้); ถ้าไม่ตั้งจะข้าม integration และยังรันทดสอบ policy/parsers ตามปกติ เมื่อขึ้น VPS ให้ `OLLAMA_URL` ชี้ Ollama เครื่องผู้ใช้ผ่าน VPN ที่อนุญาตเฉพาะเซิร์ฟเวอร์ (ทั้งแชตและประวัติ) ไม่ชี้ localhost ของ VPS

## ส่วนที่ทำงานแล้ว

- หน้า `/artists` แสดงชื่อ ประเภท แนวเพลง ประวัติสั้น และลิงก์แหล่งอ้างอิง; หน้า `/artists/[slug]` แสดงประวัติแบ่งหัวข้อพร้อมลิงก์ต้นทางใต้แต่ละช่วง รวมถึงคอนเสิร์ตและบัญชีทางการ รอบตรวจฐานข้อมูล 29 ก.ย. 2569 พบประวัติ **37/37 โปรไฟล์ รวม 117 ช่วง** (อย่างน้อย 3 ช่วงต่อคน/วง; [อ๊ะอาย 4EVE](http://localhost:3000/artists/aheye-4eve) มี 7 ช่วง) จาก URL อ้างอิง 51 แห่ง และไม่มี URL ที่ไม่ใช่ HTTPS; API ตัวอย่างอ๊ะอาย Tilly Birds MILLI และ Punch ส่งช่วงประวัติจริง Seed เพิ่มเฉพาะช่วงที่ยังว่างโดยไม่ทับข้อความที่ผู้ดูแลแก้ไว้ ความยาวประวัติขึ้นกับหลักฐานที่หาได้ ไม่อ้างว่าครอบคลุมชีวิตศิลปินทุกเหตุการณ์
- หน้าโปรไฟล์ ค้นหา/กรองศิลปินและคอนเสิร์ต ข่าว สถานะแหล่งข้อมูล บัญชี/ติดตามศิลปิน/บันทึกงานที่เคยไป รอบแสดง และผู้ดูแลเพิ่มหรือแก้ข้อมูลผ่านหน้าเว็บ/API
- ดึงคอนเสิร์ตจากหน้าเว็บสาธารณะโดยตรวจ robots.txt, อ่าน JSON-LD และรูปแบบ Eventpop ที่ตรวจพบจริง; เก็บ URL ต้นทางและเวลาตรวจ; กัน URL ซ้ำและจับคู่ชื่อกับวัน; เก็บสถานะเลื่อน/ยกเลิก; คงข้อมูลเดิมเมื่อแหล่งล้มเหลว
- นำแนวคิดจาก provider Python เดิมมาเพิ่มตัวอ่านราคา JSON-LD หลาย offer โดยไม่แปลงราคาที่ไม่มีเป็นศูนย์, Eventpop Open Graph, หน้า `/p/{id}` ของ The Concert และวันเวลา/สถานะ/ราคาของ [Ticketmaster Discovery API](https://developer.ticketmaster.com/products-and-docs/apis/discovery-api/v2/); The Concert หา ID จาก [ฟีดรายการแนะนำสาธารณะ](https://cdn.theconcert.com/v3/concerts/en/highlight.json) ของเว็บ แล้วอ่านหน้างานเดี่ยวที่ robots.txt อนุญาต; ตัวอ่าน Ticketmelon ใช้ sitemap สาธารณะและข้อมูลที่ฝังในหน้างาน โดยจำกัดการตรวจ 60 URL ที่แก้ล่าสุดต่อรอบและเก็บราคาที่ไม่พบเป็นค่าว่าง; ตัวทดสอบ parser/robots 14 กรณีผ่าน
- ทดลองแหล่งหลัก ThaiTicketMajor, Eventpop, The Concert, Ticketmelon และแหล่งสำรอง AllTicket, Live Nation Tero ตามการเข้าถึงจริง  รอบทดสอบ 29 ก.ย. 2569 ดึงได้ ThaiTicketMajor 43, Eventpop 3, The Concert 2, Live Nation Tero 15, Ticketmelon 18, Ticketmaster ไทย 13 และ Ticketmaster ต่างประเทศตามศิลปิน 70 รายการ; หลังจับคู่ซ้ำมี 159 งานในฐานข้อมูล The Concert เก็บราคาที่พบจริง 699 และ 3,500 บาทพร้อม URL ต้นทาง ส่วน Ticketmelon ทั้ง 18 รายการเป็นงานในไทยและไม่มีราคาที่ตรวจยืนยันได้ (ยังไม่ได้เทียบครบทุกงานกับต้นทาง)
- ทดสอบ Instagram Graph กับบัญชีศิลปินที่มีลิงก์ยืนยันแล้ว: รอบ 29 ก.ย. 2569 อ่านสำเร็จ 6 บัญชีและบันทึกโพสต์ 120 รายการ (บัญชีละ 20) ในฟีดข่าว; X/Facebook ยังไม่ดึงโพสต์ เพราะไม่มี token ของแพลตฟอร์มนั้น  ไม่มีการเพิ่มลิงก์ข่าวด้วยมือ
- ทดสอบ Google Routes ผ่านตัวเชื่อมของแอปได้ระยะทางตัวอย่าง 22.3 กม. และใช้ระยะทางถนนแทนค่าที่ผู้ใช้กรอกเมื่อมีเส้นทาง; ราคาบัตร/รถ/รถไฟ/น้ำมันยังแยกประเภทตามแหล่งข้อมูลและสูตรประมาณ
- Ollama ใช้ Qwen3 8B ที่ติดตั้งในเครื่องเพื่อจัดประเภทคำถามและสรุปโพสต์ที่อ่านข้อความได้; ทดสอบร่างภาษาไทยด้วย `num_ctx=4096` และ `think=false` แล้ว แต่ประวัติชุดนี้เรียบเรียงและตรวจด้วยแหล่งข้อมูลก่อนเผยแพร่ ข้อเท็จจริงในคำตอบแชตประกอบจากฐานข้อมูลโดยตรง pgvector ใช้ embedding 1,024 มิติสำหรับค้นเอกสารเพิ่มเติม
- งบแยกบัตร รถทัวร์ รถไฟ รถส่วนตัว เครื่องบิน ที่พัก; ราคาบัตรเป็นราคาที่พบ, รถ/ที่พักตามสูตรเป็นประมาณ, ที่ไม่มีข้อมูลแสดงไม่มีราคา  Amadeus test API เรียกราคาบิน/โรงแรมเมื่อมี credentials โดยติดป้ายราคาและเวลา

## ข้อจำกัดที่ต้องทำต่อ

- โปรไฟล์ยังไม่มีภาพ เพราะยังไม่ได้ยืนยันสิทธิ์ใช้งาน; บัญชีทางการยังมีหลักฐานเชื่อมโยงเพียง 9 จาก 30 โปรไฟล์หลัก ต้องตรวจความนิยม ชื่อ/สังกัด/สมาชิกที่เปลี่ยนตามเวลา และขยายเป็น 50 โปรไฟล์ตามแผน ประวัติบางรายมีหลักฐานเฉพาะช่วงที่เป็นที่รู้จัก จึงควรเติมรายละเอียดเมื่อพบสัมภาษณ์หรือเอกสารทางการเพิ่มเติม
- แหล่งคอนเสิร์ตบางแห่งไม่ให้ข้อมูลใน HTML; ดู `/status` และ log ก่อนอ้างความครอบคลุม หน้า `/concert` ของ The Concert ไม่มีลิงก์ `/p/{id}` ใน HTML จึงใช้ฟีดรายการแนะนำของเว็บ ซึ่งครอบคลุมเพียงบางงาน และตัวอ่านหน้าเดี่ยวยังจำกัดงานรอบเดียวที่ยืนยันพิกัดภาคกลางได้; Ticketmelon ใช้เพียง 60 URL ที่แก้ล่าสุดจาก sitemap ต่อรอบ จึงยังไม่ครอบคลุมทุกงาน
- ฟีด Instagram อ่านได้เฉพาะบัญชีที่ Business Discovery เข้าถึงได้; 6 บัญชีที่ทดสอบสำเร็จยังไม่รับรองว่าบัญชีอื่นจะอ่านได้  X/Facebook มีลิงก์บัญชีบางส่วนแล้วแต่ยังไม่มี token สำหรับอ่านโพสต์; หากไม่มีสิทธิ์หรือ token หมดอายุจะแสดงสถานะตรงไปตรงมา ไม่สร้างโพสต์ตัวอย่างปลอม
- ตัวดึง X จำกัดจำนวนโพสต์อ่านตามเพดาน 350 บาท/เดือนด้วยอัตราเผื่อ 50 บาท/USD; ควรตั้ง spending limit ใน X Developer Console ด้วย เพราะค่าบริการจริงและอัตราแลกเปลี่ยนเปลี่ยนได้
- 12Go ต้องได้รับสิทธิ์ affiliate/API ก่อนเชื่อมราคาจริง  งบเดินทางใช้ระยะทางจาก Google Routes เมื่อเปิดใช้งานและมีเส้นทาง มิฉะนั้นใช้ค่าที่ผู้ใช้กรอก โดยติดป้ายราคาประมาณชัดเจน
- Google Routes ถูกเรียกเมื่อผู้ใช้ขอคำนวณงบทริปและเปิด `GOOGLE_ROUTES_ENABLED`; ระบบ cache เส้นทาง 24 ชั่วโมงและจำกัดคำขอคำนวณ 5 ครั้งต่อนาทีต่อ IP แต่ยังต้องตั้ง [daily quota ใน Google Cloud](https://developers.google.com/maps/documentation/routes/usage-and-billing) ก่อนเปิดให้ผู้ใช้ทั่วไปเพื่อคุมงบ API เดินทาง
